## Answers

1. **F1 fixed?** Yes, in V5 and V6 (D1). Before: commits. After: `HOLD_UNKNOWN` / `RAPID_GRANT_UNKNOWN`, with state byte-identical on seq/head/nonces/epoch.
2. **Legitimate-id behaviour.** All diff hunks replace reads (`x[k]` -> `own(x,k)`). No assignment was rewritten: :134, :344, :367, :411 and :445 still use bracket writes. All the containers involved (`s.creds`, `s.v5.holds`, `delegations`, `incidentReviews`, `rapid.requests`, `rapid.grants`) are plain `{}` objects (chain.mjs:107-108, plus genesis creds). None of them is a Map or an array, and `Object.hasOwn` works on null-prototype objects too. The only semantic narrowing is `typeof k === 'string'`. Stored ids are always `ID_RE`-validated strings, so a non-string key (for example an array coercing to an id) used to resolve and is now refused, which is stricter. Evidence: (a) the full suite passes 586/586; (b) with `own` forced to return `undefined`, tests/v5 goes from 175/175 to 124 pass / 51 fail, so the legitimate paths are well exercised and pass through `own`; (c) the u.mjs probe for SUSPEND -> UNSUSPEND -> HOLD_EXPIRE on a real hold gives identical results at b2377da and 80b3d23. UNSUSPEND has no direct V5 test by name, but it was covered by this probe.
3. **Remaining evidence-free Root transitions.**
   - V5: HOLD_EXPIRE. Commits only for an existing own hold that is released or expired. It is repeatable (D3) and changes no authority.
   - V5: RAPID_USE_EXPIRE. Same pattern, for ended grants.
   - V5: RAPID_USE_ACTIVATE. Needs an own PENDING request with a matching digest, a met owner quorum, the same epoch, an open window and the rate limit not reached. This is by design (the quorum was already collected).
   - V4: RECOVERY_EXPIRE, GOV_EXPIRE, GOV_CASE_EXECUTE. Each needs the open case/gcase id and digest plus a deadline or state condition (`caseMatch`/`gcaseMatch` compare against a single object, with no keyed lookup). By design.
   - V3 handlers without their own signature check (RECOVERY_OVERRIDE, RECOVERY_REPLAN [guardian-signed], RECOVERY_COMPLETE, RECONSTITUTE): RECOVERY_REPLAN needs guardian approvals. The others need an open case with a matching digest and already-collected evidence. In V4/V5, RECOVERY_COMPLETE and RECONSTITUTE are V4 handlers. RECOVERY_OVERRIDE passes through.
   - Every other type needs approvals, an attestation or a signature.
   - With crafted inherited ids, none of these commit (fuzz: 0/1764). V6 adds no handlers. Its `checkGates` does no type-keyed lookup.
4. **--open-edge.** No injection found. The secret-exposure surface is the process command line, which is documented, plus audit logs and Edge history, which are not documented (D4). The no-flag and non-Windows paths are unchanged, apart from the intended clipboard opt-in. `--demo` selftest: exit 0, `[selftest] demo mode: bridge secret absent from the terminal output`, 7 bridge approvals clicked, independent V6 verifier ok=true, HOLD_RELEASE accepted. My own greps of the log: no 48-hex string, `#t=` appears only as `#t=<per-run secret, redacted>`, no `/var/tmp`, `/root` or `/home` paths. There is no `#t=<hex>` in the evidence dir, and `.demo-bridge-url` was removed at exit. Note: the selftest first failed with `ERR_MODULE_NOT_FOUND .../integrations/external-interactor/dist/harness/mockWorld.js`, because dist is gitignored and was not built in a fresh worktree. After `npm run build` in integrations/external-interactor it passed. A fresh-checkout runbook needs that build step.
5. **Full suite** (`node --disable-warning=ExperimentalWarning --test` in /var/tmp/rr): **tests 586, pass 586, fail 0, cancelled 0, skipped 0**, duration 74.5 s. The OS-isolation tests passed outside <cloud-tmp>. The previous test-107 flake did not recur.
