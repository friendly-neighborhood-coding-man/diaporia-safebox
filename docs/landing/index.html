Compromise the app.
Not the authority.

A software update can be compromised. A developer account can be stolen. The user's sensitive authority should not automatically follow either of them.

SafeBox is researching a deliberately sealed, minimal, default-deny sensitive core to limit damage when the application itself becomes untrusted.

THE SAFEBOX DESIGN PRINCIPLE
01 / Roadmap at a glance

From bounded approvals
to a sealed authority core.

SafeBox is progressing from tested, mock-based authorization boundaries toward a deliberately closed sensitive zone. Each step below is a project milestone, not a claim that production isolation is already proven.

  1. 01
    BUILT · MOCK TESTED
    CURRENT / FROZEN V6

    Bounded approvals

    Scoped MCP prepares requests. The owner approves exact actions. Replay checks, limits, a 600-second buffer and Emergency Freeze run against a MOCK ledger.

    Interface-level evidence · no real funds
  2. 02
    RESEARCH · NOT DEPLOYED
    NEXT / HARDENING

    Hard sensitive zone

    Separate OS identities, protect keys and policy state, and admit only a narrow set of typed requests. No general-purpose execution interface.

    V2/V3 isolation research ≠ V6 isolation
  3. 03
    PLANNED · NOT VERIFIED
    FUTURE / SEALED EPOCHS

    Immutable core

    Execute only verified bytes. Replace sealed versions through an independently approved update path, with protected state and anti-rollback checks.

    No claim of tamper-proof execution today
  4. 04
    RELEASE GOAL · UNPROVEN
    TARGET / DAMAGE CONTROL

    Contain compromise

    Even after a hostile app update, constrain sensitive effects with independent spending limits, freeze and recovery. Measure the remaining damage.

    Requires adversarial, independent validation
What is not yet demonstrated: V6 OS isolation, sealed executable updates, hardware-independent signing or real-chain containment. 02 / Why this matters

What if the trusted update is the attack?

We do not assume a malicious developer. We assume a well-intentioned developer can lose control of a repository, CI/CD, signing process or update channel. A valid signature can still accompany harmful code if the authority behind it was compromised.

ASSUMPTION A✳

Compromise is possible.

Supply-chain exposure is not limited to malicious prompts. An attacker may gain the ability to ship legitimate-looking updates and run code inside a trusted application.

ASSUMPTION B✳

Authority must be separate.

The app may be allowed to propose a transaction without having the ability to rewrite spending policy, sign arbitrary transfers or replace the component enforcing those restrictions.

A REAL-WORLD MOTIVATION2026

The NIKKE PC launcher security incident

In November 2026, the publisher reported tampered launcher scripts and malware distribution. Independent analysis described malicious activity running through the legitimate launcher process. The example motivates a broader threat model: what happens when trusted software delivers untrusted behavior?

Official NIKKE security notices ↗  Bitdefender analysis ↗
IMPORTANT DISTINCTION

This incident is not evidence of malicious intent by NIKKE's developers, and SafeBox does not claim to have reproduced or prevented the NIKKE attack. It is an example of why a compromised distribution path belongs in our threat model.

03 / Planned design

Close the sensitive zone. Deliberately.

Everyday agent behavior should be flexible. Changes to spending authority, policy or the security core itself should be rare, explicit and inconvenient by design.

01 / MINIMIZE

Deny by default

Keep a small command vocabulary. No arbitrary shell, filesystem, policy editing or signing interface for the app or agent.

02 / SEPARATE

Protect authority

Use OS-enforced principals and protected keys and state. Merely putting the same privileges in a second process is not isolation.

03 / SEAL

Replace, don't patch

Verify the exact bytes the trusted component consumes. Plan separately staged, owner-authorized core epochs rather than ordinary hot-updates.

04 / CONTAIN

Bound the damage

Preserve spending limits, single-use approvals, freeze capability and rollback-resistant state. Fail closed when trust cannot be established.

What stays fixed?

The core's executable code, identity of its trust roots, and rules governing who is allowed to change authority—within a given sealed epoch.

What must still change?

Spent budgets, used nonces, freeze state, audit checkpoints and security version numbers. These require protected, monotonic updates—not an immutable database.

04 / Open research

We publish the counterexamples, too.

SSTP's deterministic race improvements are meaningful, but the independent follow-up found remaining writable-mapping, coarse-timestamp and inode-reuse bypasses. An owner-log identity claim also failed under inode reuse. We will not turn partial evidence into a full security claim.

Planned next: use only verified bytes, independently protect update and execution authority, test legitimate updates and recovery, then independently measure the residual damage.

  • SSTP verifier PR #34 — PARTIAL, not tamper-proof
  • Legacy hardening PR #32 — owner-log F9 claim failed
  • Isolation documentation PR #33 — design only
  • Track D signed-launcher exercise — BLOCKED_BY_SAFETY_GATE / NOT_RUN
  • Kernel compromise, hostile app UI, real-funds containment and hardware-isolated approval — not demonstrated
THE INTENT

Make compromise survivable.
Not impossible.

SafeBox is an early research prototype, not a commercial wallet or completed isolation product. Its release objective is simple: a developer should not be able to confer a user's spending authority on an attacker merely by losing control of an application update.
